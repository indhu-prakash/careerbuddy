CareerBuddy: High-Level Design

Version 2.0 (as built) Date 2026-10-31 Status Implemented: F1–F7 Companion LLD.html Related ARCHITECTURE.md (option evaluation), PLAN.md, feature-plan/
About this document This HLD describes the system as it is implemented in this repository. ARCHITECTURE.md records the options we evaluated and why we chose them. Where the build differs from that evaluation, for example the LLM provider or synchronous AI calls instead of a job queue, this document follows the code and states the reason in §12.

1. Summary and scope

CareerBuddy helps students and working professionals move into a new role. A user uploads a resume and pastes real job descriptions (JDs) for the role they want. CareerBuddy then:

  • shows a skill-gap map backed by evidence;
  • builds a week-by-week learning plan that fits the user's available hours;
  • suggests portfolio projects that close several gaps at once;
  • runs mock interviews scored against a rubric;
  • adjusts the plan as progress comes in;
  • tracks job applications and reports which kinds of application get responses.

2. Design principles

PrincipleHow the build applies it
The LLM extracts and writes; code decidesGap scores, priorities, the week schedule, which projects are chosen, interview scores, replan triggers, skill levels and application statistics are pure TypeScript functions in src/lib/scoring/ with unit tests. The LLM turns documents into structured data and writes prose: week goals, questions, feedback.
Evidence or it didn't happenExtracted skills and requirements carry a verbatim quote, and the server checks the quote really is in the source. A JD requirement is kept only if its quote, or the skill name, appears in the JD. A resume skill whose quote fails is downgraded to "mentioned".
Extract once, reuseResumes and JDs are hashed, so a document seen before is never sent to the LLM again. Every AI result is cached per user by input hash in ai_calls.
Degrade, don't failWhen the LLM is unavailable, plan week text falls back to templates and the interview summary falls back to a narrative built from the computed numbers. Everything deterministic keeps working.
One gateway for AIEvery LLM call goes through runAiTask(), which handles caching, the per-user budget, the model fallback chain, schema validation and logging.
Simple firstModular monolith, one repo, one deployable, one database. No microservices, queues, vector database or agent framework.

  IN->>DB: job_descriptions, job_requirements
  IN->>DB: load user_skills, related edges, role-track prior if fewer than 3 JDs

The request is synchronous (maxDuration 300 s) and costs 0–2 LLM calls. If the user supplies fewer than 3 JDs and the target role matches a seeded role track, the track's skills fill in demand, weighted \(w = (3-n)/3\). This avoids a one-JD gap map that misses obvious fundamentals.

6.2 Learning plan and projects (F3, F4)

flowchart LR
  G["Ranked gap items"] --> S["scheduleLearning: prerequisites, tasks per level, capacity = 68% of hours"]
  S --> W["Week skeleton + deferred skills"]
  W --> R["Attach curated resources and topics (taxonomy)"]
  R --> T["plan.weeks: 1 LLM call writes text for all weeks"]
  T --> V["learning_plan version N+1 (active); previous superseded"]
  V --> P["projects.ideas: 5-6 candidates"]
  P --> C["Weighted set cover picks 2-4"]
  C --> M["Milestones placed into reserved 20% project time"]

Code decides what is learned in which week. The LLM only writes text for each week, and it cannot change skills, hours or tasks. If a skill doesn't fit in the time available, it is deferred and shown to the user; the plan is not compressed into something unrealistic.

6.3 Mock interview (F5)

stateDiagram-v2
  [*] --> in_progress: POST /interviews (1 LLM call writes 3-8 questions)
  in_progress --> in_progress: POST answers (1 LLM call each, optional follow-up)
  in_progress --> completed: POST complete (1 summary call, template fallback)
  in_progress --> abandoned: complete with no scored answers
  completed --> [*]
  abandoned --> [*]

Code chooses each question's type and focus skill, cycling through the session kind and the user's open gaps. The LLM scores each rubric criterion from 1 to 5, and code computes the overall score. A criterion scoring 2 or lower triggers a follow-up question, at most 2 per session. Voice answers are transcribed first, and the user can edit the text before submitting. Each interview score becomes "assessed" evidence for the skill.

6.5 Application tracker (F7)

Each application records its company, role, segment fields, source, whether the resume was tailored, and the match score frozen at the time of applying. Every stage change is an event. Statistics are computed in code. For each segment value (role family, seniority, source, industry, company size, tailored, match band), the response rate is smoothed toward the overall rate so that small samples don't mislead:

\[ \tilde r = \frac{r + k\,p}{n + k},\qquad k = 5,\; p = \text{overall response rate} \]

A segment is reported only when \(n \ge 5\). AI advice is opt-in. The model sees only the computed segment numbers, is told to quote sample sizes and to describe associations, not causes. A daily cron marks applications as ghosted after 21 days with no activity.

7. Data architecture

  • One Postgres database, accessed only from the server through Prisma. RLS is enabled with no policies on all 26 tables, which closes Supabase's public Data API.
  • Ownership: every user-owned table has userId with ON DELETE CASCADE from users, and users.id is the Supabase auth id. Deleting the account removes all of the user's data.
  • Relational for anything that is filtered or aggregated: user_skills, job_requirements, gap_items, plan_tasks, interview_evaluations, progress_events, application_events, ai_calls.
  • JSONB, validated with Zod, for LLM documents that are always read whole: parsed resume, week content, project spec, rubric and criteria.
  • Versioning instead of mutation: learning plans have version, parentId, status (draft, active, superseded) and changeSummary.
  • Append-only event log: progress_events (8 kinds) drives skill levels, streaks, hours charts and replan triggers.
  • Shared curated taxonomy: 119 skills with aliases, 1,129 tiered topics, prerequisite and related edges, and 121 link-checked resources. There are 13 role tracks with skills per tier, required level, core or recommended, and choice groups. All of it is seeded from prisma/seed/data/*.json.

8. AI architecture

8.1 A workflow, not an agent

Code runs every step and assembles all the context before calling the model. The model has no tools. It fills a JSON schema, and the result is validated before it is used. There is no LangChain, LangGraph or agent loop.

flowchart LR
  M["Module service"] -->|"runAiTask(task, promptVersion, schema)"| C{"Cache: same user + task + sha256(input)?"}
  C -- hit --> OUT["Validated result (free)"]
  C -- miss --> B{"Daily budget: under AI_DAILY_REQUEST_LIMIT?"}
  B -- no --> E429["429 ai_daily_limit"]
  B -- yes --> P1["Primary model: strict json_schema"]
  P1 -- "429/5xx: retry 3 s, 8 s" --> P1
  P1 -- "failed / invalid" --> P2["Fallback model: json_object + schema in prompt"]
  P1 -- ok --> V["finish_reason, JSON parse, Zod"]
  P2 --> V
  V --> LOG["ai_calls row: outcome, tokens, cost, latency, result"]
  LOG --> OUT

8.3 Request budget

OpenRouter's free tier allows about 50 requests a day per account, or 1,000 after buying credits. Each user is limited to AI_DAILY_REQUEST_LIMIT calls per UTC day (default 20). Cache hits are free.

9. Security and privacy

ConcernControl (as built)
AuthenticationSupabase magic link with PKCE. Middleware refreshes the session cookie on every request. withUser() verifies JWT claims (getClaims) on every API call; pages redirect to /login.
Isolation between usersThe user id comes only from the verified session. Every query is scoped by userId. Another user's id returns 404. RLS with no policies blocks the Data API.
FilesPrivate bucket with paths under {userId}/; ownership is checked and path traversal rejected; download links are signed and last 60 s; uploads are capped at 4 MB per request; text-only parsing of PDF and DOCX.
Prompt injectionDocuments are wrapped in tags and declared as data; output is constrained by a schema; the model has no tools; context is built per user.
SecretsOpenRouter, database and Supabase secret keys are server-only (import "server-only"). Cron routes require Bearer CRON_SECRET and refuse requests when it is unset.
Cost abusePer-user daily AI limit; Zod length caps (answers ≤ 10,000 chars, JD text ≤ 30,000 chars)
PrivacyDELETE /api/v1/me removes the user's files, then the user row (which cascades), then the auth user. Audio is never stored. Free models are used with demo data only.

10. Non-functional requirements

AttributeTarget / behaviour
Latency, non-AISingle indexed queries per request; Prisma pool of 3 per instance
Latency, AIFree models take about 30–60 s per call. Routes allow up to 300 s and the UI shows progress states. A paid model is the lever if this needs to be faster.
CorrectnessAll AI output is schema-valid or the call fails with a typed error; 150 unit tests cover the scoring, scheduling and service logic
AvailabilityBest effort on free tiers. When the LLM is down, the deterministic features and stored data keep working.
ScalabilityThe first limit is LLM quota. Moving to Vercel Pro, Supabase Pro and paid models needs no code changes.
Accessibility and UXResponsive layouts, light and dark themes, print-friendly gap map
