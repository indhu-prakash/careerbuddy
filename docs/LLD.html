2. Cross-cutting design

2.1 Route handler pipeline

Every /api/v1 handler is built with one wrapper so that auth, validation, error mapping and tracing behave the same everywhere.

// src/lib/http/route.ts
export function withRoute<B extends z.ZodType | undefined, R>(
  opts: { body?: B; query?: z.ZodType; ai?: boolean },               // ai: apply the AI rate limit
  handler: (ctx: { user: User; body: InferOrVoid<B>; params: Record<string, string>; traceId: string }) => Promise<R | Response>,
) {
  return async (req: Request, { params }: { params: Promise<Record<string, string>> }) => {
    const traceId = crypto.randomUUID();
    try {
      assertSameOrigin(req);                       // CSRF: mutations must carry our Origin
      const user = await requireUser();            // exists in src/lib/auth.ts
      if (opts.ai) await rateLimit(user.id);       // 10 AI requests/min per user (ai_calls count)
      const body = opts.body ? opts.body.parse(await req.json()) : undefined;
      const result = await handler({ user, body, params: await params, traceId });
      return result instanceof Response ? result : Response.json(result);
    } catch (err) {
      return toProblemResponse(err, traceId);     // §2.2
    }
  };
}

// src/app/api/v1/target-roles/[id]/jds/route.ts
export const POST = withRoute({ body: AddJdRequest }, ({ user, body, params }) =>
  jobsService.addJobDescription(user.id, params.id, body));

2.2 Errors

Services throw AppError(code, status, safeMessage, details?). toProblemResponse maps it to RFC 9457 application/problem+json with traceId. ZodError becomes VALIDATION_FAILED; Prisma connection errors become DB_UNAVAILABLE; anything else becomes INTERNAL with no stack trace.

3.2 AiService.run

// src/lib/ai/service.ts
export async function run<T extends AiTask>(
  task: T, input: TaskInput<T>, ctx: { userId: string; signal?: AbortSignal },
): Promise<{ data: TaskOutput<T>; callId: string; cached: boolean }> {
  const def = TASKS[task];                                    // prompts/<task>.ts
  const route = ROUTES[task];
  const inputHash = sha256(`${task}|${def.promptVersion}|${canonicalJson(input)}`);

  // 1. cache: same task + prompt version + input = same answer, 0 requests
  const hit = await db.aiCall.findFirst({
    where: { inputHash, outcome: { in: ["ok", "repaired", "fallback"] }, purgedAt: null },
    orderBy: { createdAt: "desc" },
  });
  if (hit) { await logCall({ ...base, outcome: "cache_hit" }); return { data: def.schema.parse(hit.result), callId: hit.id, cached: true }; }

  // 2. budget: counted from ai_calls rows since 00:00 UTC (provider resets daily)
  await assertBudget(ctx.userId);                             // throws AI_QUOTA_EXHAUSTED with resetAt

  // 3..7. provider chain with one repair attempt per model
  const prompt = def.build(input);
  let issues: string[] = [];
  for (const [i, ref] of route.chain.entries()) {
    for (let attempt = 0; attempt <= (route.repair ? 1 : 0); attempt++) {
      const res = await provider.generate({ ...ref, ...prompt, schema: def.schema,
        repairNotes: attempt ? issues : undefined, maxTokens: route.maxTokens, effort: route.effort, signal: ctx.signal });
      await logCall({ ...base, model: ref.model, requests: res.requests, latencyMs: res.latencyMs,
        tokens: res.usage, outcome: res.ok ? "pending" : res.reason });
      if (!res.ok) { issues = [res.error]; if (res.reason === "invalid") continue; break; }

      issues = def.validate(res.data, input);                // §3.4: quotes, ID whitelist, ranges
      if (issues.length === 0 || def.tolerant) {             // tolerant: drop bad items instead of failing
        const outcome = i > 0 ? "fallback" : attempt > 0 ? "repaired" : "ok";
        const callId = await finaliseCall(outcome, res.data);
        return { data: res.data, callId, cached: false };
      }
    }
  }
  throw new AppError("AI_UNAVAILABLE", 503, "The AI service could not produce a valid result. Please retry.");
}

Every HTTP request to OpenRouter (including retries inside the provider) adds to the requests column, so the budget check counts real usage: SUM(requests) WHERE created_at >= today_utc.

3.3 OpenRouter provider

The existing generateStructured() in src/lib/ai/client.ts already implements the per-model call: strict json_schema for the primary, json_object with the schema embedded for the fallback, 429/5xx retries (3 s, 8 s), finish_reason === "length" rejection, fence stripping and Zod parsing. Its public signature stays as it is (the CLI uses it). The provider is a thin layer over the same internals that:

  • calls one model per invocation (the chain moves to AiService), and returns a result object instead of throwing, with reason: "invalid" | "truncated" | "http" | "timeout" | "refusal";
  • appends repair notes as a second user message: "Your previous output had these problems: … Return the corrected JSON only.";
  • reports usage from the response body and the number of HTTP requests made, including retries.

3.4 Validators

// src/lib/ai/validators/quote.ts
const norm = (s: string) => s.normalize("NFKC").toLowerCase()
  .replace(/[\u2018\u2019]/g, "'").replace(/[\u201C\u201D]/g, '"').replace(/[\u2013\u2014]/g, "-")
  .replace(/[•▪◦·]/g, " ").replace(/\s+/g, " ").trim();

/** True when the quote appears in the source after normalising case, whitespace, quotes and bullets. */
export function verifyQuote(source: string, quote: string): boolean {
  const q = norm(quote);
  return q.length >= 3 && norm(source).includes(q);
}

3.5 Output schema rules

  • Use .nullable(), not .optional(): strict JSON-schema mode expects every property to be required.
  • Closed sets are z.enum; strings have .max(); arrays have .max(), which caps output tokens.
  • Each extraction schema has an explicit "unknown" path: yearsExperience: z.number().nullable(), insufficientContent: z.boolean().
  • A unit test runs z.toJSONSchema() on every task schema and checks it is accepted in strict mode (no unsupported keywords, all properties required).
  • Prompts wrap documents in tags (<resume>, <job_description index="n">, <answer>) and state that tag content is data, not instructions.

4. Async AI jobs

Intake and roadmap generation can take more than 30 seconds, so the endpoint answers 202 {jobId} and the work continues in after() (stable in Next.js 15.1+; route files set export const maxDuration = 300).

stateDiagram-v2
  [*] --> queued: POST creates ai_jobs row
  queued --> running: after() starts, updatedAt heartbeat
  running --> ready: all steps done
  running --> failed: error or AI_UNAVAILABLE
  running --> failed: heartbeat older than 6 min (checked lazily on poll)
  failed --> queued: POST .../retry (idempotent, redoes missing parts only)
  ready --> [*]

// src/lib/modules/jobs-queue/service.ts
export async function startJob(userId: string, kind: JobKind, refId: string, work: (j: JobHandle) => Promise<void>) {
  const running = await db.aiJob.findFirst({ where: { userId, kind, refId, status: { in: ["queued", "running"] } } });
  if (running) return running;                                     // idempotent: same job id back
  const job = await db.aiJob.create({ data: { userId, kind, refId, status: "queued" } });
  after(async () => {
    const handle = jobHandle(job.id);                              // progress(n,total), heartbeat
    try { await handle.start(); await work(handle); await handle.done(); }
    catch (e) { await handle.fail(safeMessage(e)); }
  });
  return job;
}

Polling: GET /api/v1/jobs/{id} returns {status, progress, total, refId, error?}. The UI polls every 2 s with TanStack Query and stops on ready or failed.

5.2 Jobs (F2)

  • addJobDescription(userId, roleId, {text, company?, title?, url?}): cap 30k chars; contentHash = sha256(normalised text); duplicate returns the existing row (0 requests). If the resume is already processed, start a jd.extract job; otherwise the JD waits for the combined intake call.
  • Each extracted requirement becomes a job_requirements row {jdId, userId, skillId, kind, levelHint, quote}. Requirements whose quote fails verification are not stored.
  • A JD with insufficientContent=true or no verified requirements gets status=needs_detail and is excluded from demand.
  • URLs are stored for reference only. Import from Greenhouse/Lever public APIs is a stretch goal; other sites are never scraped.

5.3 Gap scoring (F2)

Extends src/lib/scoring/gap.ts with a level-based scorer, scoreGapAnalysis(). The existing scoreGaps() stays for the CLI until it moves to levels. For canonical skill \(s\) over \(N\) usable JDs, where \(w_j(s) = 1\) if JD \(j\) requires \(s\), \(0.5\) if it is nice to have, and \(0\) if absent:

\[ \text{demand}(s) = \frac{1}{N}\sum_{j} w_j(s) \qquad \text{req}(s) = \operatorname{median}_j(\text{levelHint}_j(s)) \;\; (\text{default } 2) \qquad \text{cur}(s) = \text{skill\_levels.level} \;\; (0 \text{ if absent}) \]
\[ \text{gap}(s) = \frac{\max(0,\ \text{req}-\text{cur})}{4} \qquad \text{priority}(s) = \text{demand}(s)\cdot\text{gap}(s)\cdot\bigl(1 + 0.5\cdot\text{isFoundation}(s)\bigr) \]
\[ \text{match} = \frac{\sum_s \text{demand}(s)\cdot\min(\text{cur},\text{req})/\text{req}}{\sum_s \text{demand}(s)} \]
Derived fieldRule
statusmatched if cur ≥ req; partial if 0 < cur < req; missing if cur = 0
gapBandLow ≤ 0.25 < Medium ≤ 0.5 < High
categorymust_have if required in ≥ 50% of JDs; else advanced if req ≥ 3; else domain if the skill's category is domain; else good_to_have
isFoundationThe skill is a prerequisite (skill_edges.kind=prereq) of another skill with gap > 0.25
transferableRelated skills (kind=related) where cur ≥ 2, shown as an Estimate with a 30% ramp-up reduction
evidenceJD quotes per requirement + resume quote, so every cell links to its source
lowEvidenceTrue when N < 3; UI shows "add at least 3 JDs for reliable priorities"

The result is stored in gap_analyses with version = previous + 1 and inputHash = sha256(skill levels + requirement ids); an unchanged input returns the latest version instead of a new one.

5.4 Roadmap scheduler (F3)

// src/lib/planning/scheduler.ts  (pure)
const HOURS_PER_LEVEL: Record<SkillCategory, number> = {
  language: 10, framework: 8, cloud: 6, tool: 5, concept: 6, domain: 5, soft: 3,
};

export function schedule(input: {
  gaps: GapItem[]; edges: SkillEdge[]; categories: Map<string, SkillCategory>;
  hoursPerWeek: number; durationWeeks: number;
}): { weeks: WeekSkeleton[]; notCovered: { skillId: string; hours: number }[]; suggestedWeeks: number } {
  // 1. units: one per gap skill, hours = levels to close x rate, -30% if a related skill is at level 2+
  const units = input.gaps.filter(g => g.gap > 0).map(g => ({
    skillId: g.skillId, priority: g.priority,
    hours: (g.req - g.cur) * HOURS_PER_LEVEL[input.categories.get(g.skillId) ?? "concept"] * (g.transferable.length ? 0.7 : 1),
  }));
  // 2. order: topological sort on prereq edges; ties broken by priority desc (Kahn's algorithm)
  const ordered = topoSort(units, input.edges, (a, b) => b.priority - a.priority);
  // 3. capacity: 85% of stated hours, minus 1 h checkpoint; from the midpoint 25% goes to the project
  const capacity = (w: number) => {
    const base = input.hoursPerWeek * 0.85 - 1;
    return w >= Math.ceil(input.durationWeeks / 2) ? base * 0.75 : base;
  };
  // 4. pack: fill weeks in order, splitting a unit across weeks when it is larger than what is left
  // 5. anything left after the last week goes to notCovered (lowest priority first is dropped);
  //    suggestedWeeks = weeks needed to fit everything at the same pace
}

Units are never compressed to fit. Rejection rule: if < 50% of must-have hours fit, the plan is still created but the UI leads with the "not covered" list and the suggested horizon.

Service roadmapService.generate(userId, {gapAnalysisId, durationWeeks ∈ {4,8,12,16}, hoursPerWeek 2–40}): run the scheduler, insert learning_plans(status=generating), plan_weeks(status=pending) and placeholder tasks in one transaction, then start job roadmap: roadmap.content per chunk of ≤ 8 weeks, then projects.generate. On success, mark the plan active and the previous active plan superseded in one transaction. On failure, weeks without content stay pending; POST /roadmaps/{id}/retry regenerates only those.

5.5 Projects (F4)

  • Clusters (code): take the top 8 gaps by priority. Beginner tier = the 2–3 highest-priority must-have gaps with the lowest req; Intermediate = next 3 with a prereq link to beginner skills where possible; Advanced = the remaining high-priority gaps plus any advanced-category gap.
  • LLM: one projects.generate request writes all three specs; skill IDs are whitelisted.
  • Coverage check (code): every top-5 gap must appear in a plan task or a project's skillIds; otherwise a task for it is added to the earliest week with spare capacity, or it is listed in "not covered".
  • Starting a project turns its milestones into plan_tasks(kind=project_milestone) in the reserved project capacity.

Strong skillFirst checkpoint ≥ 85% and an interview technical-accuracy ≥ 4 on that skillCut that skill's remaining hours by 30%
Falling behindLogged hours < 75% of planned for 2 consecutive weeksRe-pack at observed pace; offer "extend by N weeks" or "drop X"
Ahead> 120% for 2 weeksOffer to pull the next units forward

A trigger creates a plan_revisions(status=proposed) row with the new skeleton, a diff (planning/diff.ts: added, removed, moved tasks per week) and a reason built from the trigger's numbers. Accepting it: roadmap.revise writes content for the affected weeks, then a new learning_plans row with version+1, parentId, reason is created. Done tasks are copied unchanged.

Readiness index (scoring/readiness.ts), each component in [0, 1] and shown separately in the UI:

\[ R = 100\,(0.4\,C + 0.3\,I + 0.2\,P + 0.1\,M) \]

\(C\) = match score using current levels, \(I\) = EWMA (\(\alpha = 0.5\)) of the last 5 session scores / 100, \(P\) = done task hours / planned hours to date, \(M\) = done project milestones / total.

5.8 Applications (F7)

  • Status pipeline: saved → applied → screening → interviewing → offer, or rejected | ghosted | withdrawn from any active stage. Each change writes an application_events row; ghosted is suggested (not set) after 21 days with no event.
  • matchScoreAtApply is copied from the latest gap analysis when the application is created.
  • Stats (scoring/stats.ts, pure): per segment value, callback rate = reached screening or later / applied; interview conversion = interviewing / screening; Wilson interval at 95% (formula in HLD §6.5).
  • Gates: total < 10 → counts only; segment n < 5 → "not enough data"; comparison only if both n ≥ 5 and intervals don't overlap.
  • Text: templates such as "{segA} had {kA}/{nA} callbacks vs {kB}/{nB} for {segB}. This is an association; role and timing may explain it." No LLM request.

5.9 Report CLI

scripts/analyze.ts (exists) writes analysis.json; build_report.py (exists) turns it into Excel and PDF. The JSON is the contract between them: {generatedAt, promptVersion, sources, candidate, matchScore, gaps[{skill, demand, have, gap, status, evidence}], jobDescriptions, recommendations}. When the app adds GET /gap-analyses/{id}/export, it emits the same shape (with an added level/required pair), so the Python script works on app data without changes. The Python step never runs on Vercel.
